# ADR-0008 — Background jobs are in-process and database-backed

## Context

Long-running work comes in three shapes: agent jobs (rewrite, extraction per target, breakdown, video-prompt batch), generation tasks, and merges. If agent-job state lived in process memory, a restart would leave the UI polling forever; generation tasks, by contrast, are database rows that can be failed at boot (`adr-0005`).

## Decision

All background work is **in-process** (no external queue) and **database-backed**:

- `agent_jobs` rows for rewrite / extraction / breakdown / prompt batch, with `running | done | failed`, progress JSON and timestamps; one active job per (kind, episode, target). Starting a duplicate returns the running job with `alreadyRunning: true` (HTTP 200) for every kind — so the UI never has to special-case a conflict.
- `generation_tasks` and `films` keep their own tables because they carry provider or encoder state.
- At boot, every row still `running`/`processing` is marked failed with an "interrupted by a restart" message.
- The web app polls one endpoint per episode for job status and per-task endpoints for generation.

## Alternatives Considered

- **In-memory job maps.** Rejected: not restart-safe, three ad-hoc status endpoints.
- **BullMQ / Redis or a workflow engine.** Rejected for a single-user, single-process tool; the job wrapper isolates the choice so a queue can be added if multi-process deployment is ever needed.
- **Server-sent events instead of polling.** Deferred; polling with bounded intervals is simple; SSE can be layered on the same tables.

## Consequences

- Uniform restart semantics and one place to look for "what is running" (`GET /episodes/:id/jobs`, the `EpisodeJobs` read model).
- Jobs that replace data (storyboard breakdown) park the old rows under the job id and restore them on failure, so an interrupted job never loses generated work.
- Progress for batches is visible without extra endpoints.
- The API process is stateful (polling loops); horizontal scaling is out of scope.
