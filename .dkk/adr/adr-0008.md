# ADR-0008 — Background jobs are in-process and database-backed

## Context

Long-running work comes in three shapes: agent jobs (rewrite, extraction per target, breakdown, video-prompt batch), generation tasks, and merges. If agent-job state lived in process memory, a restart would leave the UI polling forever; generation tasks, by contrast, are database rows that can be failed at boot (`adr-0005`).

## Decision

All background work is **in-process** (no external queue) and **database-backed**:

- `agent_jobs` rows for rewrite / extraction / breakdown / prompt batch, with `running | done | failed`, progress JSON and timestamps; one active job per (kind, episode, target). Starting a duplicate returns the running job with `alreadyRunning: true` (HTTP 200) for every kind — so the UI never has to special-case a conflict.
- `generation_tasks` and `films` keep their own tables because they carry provider or encoder state.
- At boot, every row still `running`/`processing` is marked failed with an "interrupted by a restart" message.
- The web app polls one endpoint per episode for job status and per-task endpoints for generation.

## Alternatives Considered

- **In-memory job maps.** Rejected: not restart-safe, three ad-hoc status endpoints.
- **BullMQ / Redis or a workflow engine.** Rejected for a single-user, single-process tool; the job wrapper isolates the choice so a queue can be added if multi-process deployment is ever needed.
- **Server-sent events instead of polling.** Deferred; polling with bounded intervals is simple; SSE can be layered on the same tables.

## Consequences

- Uniform restart semantics and one place to look for "what is running" (`GET /episodes/:id/jobs`, the `EpisodeJobs` read model).
- Jobs that replace data (storyboard breakdown) park the old rows under the job id and restore them on failure, so an interrupted job never loses generated work.
- Progress for batches is visible without extra endpoints.
- The API process is stateful (polling loops); horizontal scaling is out of scope.

## Amendment (2026-10-06)

A fifth kind, `recap` (`production.RecapJob`, `adr-0014`), is keyed by episode and script revision (`target`), so a job for a newer script may start while one for an older script still runs; the older one's save is refused and it fails at once. `EpisodeJobs` shows the latest recap job whichever revision keyed it.

## Amendment (2026-10-08)

Jobs gain a scope (`adr-0015`): `outline` and `plan` belong to a drama and carry no episode, `write` and the earlier kinds belong to an episode. One active job per (kind, drama, episode-or-none, target), enforced by two partial unique indexes (drama-scoped and episode-scoped rows) and by a duplicate lookup that always filters on the drama; `runJob` asserts the kind's scope. `GET /dramas/:id/jobs` (`production.DramaJobs`) is the drama-scoped counterpart of the episode endpoint. A plan job's progress row is its state (the request and the ids added so far), so a failed or interrupted plan keeps the episodes it created and reports how many of the requested count were planned; nothing is parked or restored.

## Amendment (2026-10-09)

**Jobs can be cancelled** (`production.CancelAgentJob`, `POST /agent-jobs/:id/cancel`). Every running job holds an abort signal that reaches the model call in flight and stops tool execution. The job then settles with a fourth status, `cancelled`, through the same failure hooks: a breakdown restores its parked shots, and a plan keeps the episodes it created. Settling is compare-and-set on `running`, so whichever of finishing, failing and cancelling comes first wins.

**Agent runs are bounded and scoped.**

- Each provider call has a 10-minute step timeout, so a stalled call fails the job instead of holding it.
- A plan runs one agent run per batch of episodes.
- Per-job in-memory state (`jobState`) is dropped when its job settles.

**The script has one agent at a time.** A rewrite or a write is refused while the other writes the script, or while a breakdown or an extraction reads it. A breakdown or an extraction is refused while the script is being written. The creator's script edits follow the same rule. A project is not deleted while any of its jobs runs (`production.DeleteDrama`), since the job would go on adding episodes or assets under it.
