# ADR-0014 — Series continuity through episode recaps

## Context

A drama's assets (characters, scenes, props) are drama-scoped and reused across episodes, but the agents that write and break down an episode see only that episode: `read_episode_script` returns the raw content and the current script, `read_storyboard_context` the script and the asset ids. Nothing tells them what happened before, so a returning character is introduced as a stranger, the tone drifts and threads from earlier episodes are dropped. The drama's synopsis and genre exist in the data model but reach no agent and no screen. Most short dramas are serials; some are anthologies or standalone skits, where cross-episode memory would mislead.

## Decision

- **A drama is serial by default** (`dramas.serial`, "Episodes continue one story" in the create and edit dialogs). In a serial drama every saved script gets a **recap**: a short account (≤ 2000 characters) of what happened, written for the writers of the next episodes, stored on the episode (`episodes.recap`) and editable by the creator. A non-serial drama gets no recaps.
- **A fifth agent, `recap_writer`**, writes it in a `recap` job (`RecapJob`), through the same runtime as the other agents: editable prompt file and skill, language variants (`adr-0011`), model override, the until-saved check. It runs after the rewriter saves (`WriteRecapAfterScript`, before the rewrite job settles) and after a skipped rewrite; the creator can also write or rewrite it from the recap card. A manual script edit does not re-run it.
- **The context reaches the agents in their read tools' results**, as a `series` block built by one `SeriesContext` builder: the premise (title, synopsis, genre when set) and, for a serial drama, the earlier episodes in order, each with its recap and a status — `ready`, `stale` (the script changed since the recap was written; the text is still given) or `missing` — so gaps are named instead of silently absent. The oldest recaps are dropped beyond a character budget and listed as omitted. The API-owned user messages of the rewriter and breaker always point at the block, so workspaces whose prompt files predate it (and are never overwritten, `adr-0006`) still get the instruction.
- **Freshness is revision-based.** `episodes.scriptRevision` increments on every real change of the script, through one `writeScript` helper used by the rewriter's save tool, the creator's edit and the skip. A recap records the revision it was written for; "stale" is derived, never stored. A recap job is keyed by the revision it started from, its save is conditional on that revision still being current, and a refused save fails the job at once (no retry) — a slow recap can never claim a newer script. The creator's own edit pins to the current revision; a patch with both the script and the recap writes the script first.
- The breakdown refuses to start while a rewrite is running.

## Alternatives Considered

- **Feed the full earlier scripts.** Rejected: tens of thousands of characters per episode blow the context of the cheaper text models and bury the current episode; recaps carry what the next episode needs.
- **One rolling series summary** updated after each episode. Rejected for now: it would be rewritten (and drift) on every episode, and a creator could not fix one episode's account without touching the others. It stays in the backlog for very long series.
- **Put the context in the system prompt.** Rejected: the prompt files are the creator's, copied once and never overwritten, so a new instruction there would reach new installs only; tool results are API-owned.
- **A bare text call instead of an agent.** Rejected: an agent gets the editable prompt and skill, the language directive, the model override and the until-saved retry for free, and shows up in Settings › Agents like the others.
- **A `recapStale` flag set on script save.** Rejected: a flag cannot tell a recap written for the current script from one written for an older one when a slow job finishes late; the revision can.
- **Refuse a rewrite or breakdown until every earlier recap is fresh.** Rejected: too strict, and projects created before this decision would block; the studio shows the counts instead.

## Consequences

- The enum tables of `adr-0007` gain `AgentType.recap_writer` and `JobKind.recap`; the job kinds of `adr-0008` gain `recap`, keyed by episode and script revision (the only kind where a newer key may run beside an older one).
- `EpisodeJobs` carries the latest recap job; the studio polls it like the others, and the skip-rewrite call starts the polling.
- Projects created before this decision are serial with no recaps; their agents see `missing` entries until the creator opens the earlier episodes and writes them (the rewrite panel shows the counts).
- The series paragraph in the shipped rewriter and breaker prompt files reaches new installs only; the message sentence covers the rest.
- A breakdown has no script snapshot, so a manual script edit during a breakdown is still not detected (backlog).
