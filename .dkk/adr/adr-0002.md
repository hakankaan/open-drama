# ADR-0002 — Monorepo with a Next.js web app and a Node.js API

## Context

The product owner asked for a Next.js frontend and a Node.js backend. The web app and the API are separate processes that share a JSON contract, and a desktop shell may wrap them later. Sharing types between the two apps matters because the API contract is large (eight contexts, ~90 endpoints).

## Decision

A single repository managed as a **pnpm workspace**:

- `apps/web` — Next.js (App Router, TypeScript).
- `apps/api` — Node.js API in TypeScript.
- `packages/contracts` — zod schemas and inferred types for every request and response, consumed by both apps.
- `workspace/` — agent prompt and skill templates.
- `docs/plans/`, `.dkk/` — plans and domain model.

Node.js 20+ (22 LTS recommended). Root scripts run both apps (`dev`, `build`, `typecheck`, `lint`).

## Alternatives Considered

- **Next.js route handlers as the backend.** Rejected: the API runs long-lived background work (polling loops, FFmpeg processes, agent runs) and owns a SQLite file and a media directory; that fits a dedicated Node process better than serverless-style handlers, and it keeps the API usable without the web app.
- **Two separate repositories.** Rejected: the contract package and atomic changes across web and API are the main reason for a monorepo.
- **npm workspaces.** Viable; pnpm is faster and already installed on the team machines.

## Consequences

- One `pnpm install`, one CI pipeline, shared lint and TypeScript configs.
- The API can be deployed alone (headless) and the web app can be pointed at any API origin.
- Native modules (`better-sqlite3`, `sharp`) live only in `apps/api`.
