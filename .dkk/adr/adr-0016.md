# ADR-0016 — Two user interfaces over one service layer

## Context

Open Drama has one user interface, the web studio, and every rule a creator meets lives either in the service layer or in a route or a page. Creators increasingly work from an AI assistant (Claude Code, Claude Desktop, claude.ai, Cursor, Codex CLI) and want to run the story room from there: create a project, have the story writer draft the outline, review it in the conversation, plan and write episodes. That needs a second interface the assistants speak (MCP over Streamable HTTP), default guardrails that travel with the server, and a way to connect without handing the creator's provider keys to the assistant vendor. It also raises a question the studio never had to answer: whether the two interfaces are peers that work without each other, or whether one wraps the other.

## Decision

- **Two presentation layers over one service layer.** The studio (`apps/web`, REST over the Next proxy) and the assistant endpoint (`apps/api/src/mcp/`, MCP over Streamable HTTP) are peers. Each is a thin transport: validate with a contract schema, call a service function, map the result or the `ApiError`. Neither imports the other; the service layer never learns which one called; a rule that lives in a route or a page is a bug. **Parity rule:** every command and query in the domain model has a REST route and an MCP tool, except (a) **secrets** (an API key is never accepted over MCP), (b) **binary media** (MCP carries text: media enter through the API's upload route and leave as URLs under `/static`), (c) **one interface's own state** (tours seen, the studio's layout). Iteration 1 delivers the configuration and story-room subset; iteration 2 delivers the production floor, the agent prompt and skill editing, and `delete_drama`. The parity inventory lives in `docs/plans/README.md`.
- **The endpoint lives in the API process**, mounted at `/mcp` on the API's own port, outside `API_BASE` (the protocol carries its own version). It is **stateless**: one server instance per request, no session id, so a restart loses nothing. The web server forwards `/mcp` as it forwards `/api`; it implements nothing, and it is not needed for the endpoint to exist. A separate stdio server package was rejected: a second process to install and keep in version with the API, when every current assistant speaks Streamable HTTP (one that does not can bridge with `mcp-remote`).
- **Two deployment shapes, one exposed port each** (`adr-0010` amended). *Studio and assistant*: web on the exposed port, API on localhost, the proxy forwards `/api`, `/static`, `/mcp`. *API only*: `OPEN_DRAMA_WEB_UI=0`; in Docker the entrypoint starts the API alone on `0.0.0.0:3000`; outside Docker `OPEN_DRAMA_WEB_UI=0 HOST=0.0.0.0 PORT=3000 pnpm --filter @open-drama/api start`. A LAN name or a reverse proxy's domain goes into `OPEN_DRAMA_ALLOWED_HOSTS` in both shapes. In both shapes the raw port serves `/api` without authentication (`adr-0010`'s stance, unchanged); only `/mcp` carries a token, because it is the one path a cloud assistant needs published. `OPEN_DRAMA_ASSISTANT=0` makes `/mcp` answer 404 and changes nothing else.
- **The story room needs a text service only.** `CreateEpisode` and `PlanEpisodes` no longer refuse without an image and a video service. The lock moves to **first use**: creation and planning lock each type that has a usable service and leave the other locks empty; the first generation that needs a type resolves it as today for a missing lock (highest-priority usable service, else the existing precondition) and claims the episode's lock before any work is dispatched (compare-and-set on the empty column, the stored id read back, so two first generations racing each other both go on with the one that won), so one episode still uses one provider per type from its first shot on. Readiness keeps reporting `missingTypes`.
- **Secrets never travel through a conversation.** The MCP input schemas are the contract schemas **minus `apiKey`, strict**, so a key in a call is a schema error. A service added over MCP is listed with `hasKey: false` and is unusable until the key arrives by the studio's form, by the environment at boot (`OPEN_DRAMA_MODELRUNNER_API_KEY`, an insert-only seeder that never updates a row), or by `PATCH /api/v1/model-services/{id}` with the key read from stdin. Accepting keys over MCP was rejected: the key would land in the assistant vendor's transcript.
- **Text edits carry a freshness token: an integer revision.** The tools that save an outline, a beat sheet, a script or a recap require `ifRevision`; the service checks it inside the write transaction and refuses with `CONFLICT` when the text changed since. `outlineRevision` (dramas) and `beatsRevision` (episodes) join the existing `scriptRevision` and `recapRevision`, bumped by every write including the agents' saves. `updatedAt` was rejected as the token: two writes can share a millisecond. A recap save may also name the script revision it was written for (`forScriptRevision`, returned by the read) and is refused once the script moved on, so a recap of an older script is never pinned to a newer one.
- **Assistant skills are Markdown in the workspace** (`workspace/assistant/`, template v7), served from that one source as MCP **prompts** (one per skill directory), as MCP **resources** (`open-drama://skills/<name>`) and, for `instructions.md`, as the server's **instructions** at initialise. A Claude Code plugin generated from the same files is a distribution step, not a second source.
- **Guardrails in three layers.** (1) *Instructions*, always on. (2) *Server refusals*: revision tokens on text saves; `replace: true` on the agent runs that would overwrite a saved outline, script or fresh recap; `force: true` on deleting an episode that holds a script, shots or a film; a delete refused while a job of the episode runs; the existing locks. These protect against accidental loss, not proof of consent. (3) *Consent lives in the client*: the deleting, cancelling and service-removing tools carry `_meta["anthropic/requiresUserInteraction"]` so Claude Code always asks; other clients prompt per their settings, and the instructions say to ask in the conversation. Elicitation was rejected: it needs a stateful session.
- **Jobs stay jobs.** A tool that starts an agent returns `{ jobId, alreadyRunning }` like its route. `wait_for_job` polls up to `timeoutSeconds` (default 30, at most 300, `0` for an immediate read) and returns the job with a typed outcome per kind. `use_content_as_script` is a save returning the episode and the recap job it started.
- **The server issues the token; either interface shows it.** `/mcp` requires `Authorization: Bearer <token>`. The token comes from `OPEN_DRAMA_ASSISTANT_TOKEN` when set (at least 32 characters), else it is generated at first boot into `app_settings` and the connect line is printed once to stdout outside the logger. It is readable through `GET /api/v1/settings/assistant` (`Cache-Control: no-store, private`), shown in Settings › Assistant with a Rotate button (`POST /api/v1/settings/assistant/rotate`, which prints nothing), compared in constant time before the transport sees the request; a miss is `UNAUTHORIZED` (401). No accounts and no OAuth: Open Drama has no identity to issue one for.
- **The studio is optional in every assistant text.** `get_status` reports the studio's address or `null`; write tools return a `studioPath` the assistant links only when there is an address.
- **Paid generation is iteration 2 and opt-in**, behind a setting and per-call caps.

## Alternatives Considered

- **The assistant as a client of the studio** (a stdio server wrapping REST, or the web app hosting the endpoint). Rejected: the studio would be required for the assistant to exist, and the endpoint would die with the web process.
- **Keys over MCP.** Rejected (transcripts). **`?token=` in the URL.** Rejected (URL logs). **OAuth.** Rejected (no identity). **Elicitation for consent.** Rejected (stateful sessions, uneven support).
- **Requiring all three service types before any episode.** Rejected: it keeps a creator with only a text key out of the story room in both interfaces, for no benefit.
- **Blocking agent-start tools until the job settles.** Rejected: a client's tool timeout would decide whether a job counts.

## Consequences

- A new module `apps/api/src/mcp/`; two dependencies (`@modelcontextprotocol/sdk`, `@hono/mcp`); four environment variables (`OPEN_DRAMA_WEB_UI`, `OPEN_DRAMA_ASSISTANT`, `OPEN_DRAMA_ASSISTANT_TOKEN`, `OPEN_DRAMA_MODELRUNNER_API_KEY`); migration `0006` (three revision columns: the outline's, the beats' and the recap text's); the web proxy matcher gains `/mcp`; the Docker entrypoint learns the API-only shape; the workspace template moves to v7; the error contract gains `UNAUTHORIZED`.
- The domain gains the actor `Assistant` and the flow `AssistantStoryCreation`; `adr-0010` (two shapes, forwarded path, token), `adr-0013` (lock at first use), `adr-0006` (the assistant folder) and `adr-0008` (recap link on the write job; delete, outline and recap rules) are amended.
- Rules that both interfaces need move into the service layer: nullable locks and lock at first use, the episode delete guard, `useContentAsScript`, revision-checked saves, earlier-recap settling for script jobs, outline refused during a plan, recap replace, job existence checks.
- The token is one shared secret for every assistant; rotation revokes them all. Enough for a single-user tool; multi-user authentication stays in the backlog.
- About 36 tools in iteration 1; the parity inventory is the guard against drift between the two transports.

## Amendment (2026-10-17)

**A dead lock is replaced like an empty one.** An episode's image or video lock that names a service which was deleted,
disabled or given another type used to stay in place while every generation fell back to the highest-priority usable
service, unlocked, so the episode could drift across providers and never settle again. Now the next generation of that
type claims the lock for the service it resolves, with the same compare-and-set, compared with the dead id instead of
an empty column, so two requests racing each other still go on with the one winner. Enabling the old service again does
not bring the old lock back: the episode stays on the one it moved to. A service that is still active but has lost its
key is not dead: the request is refused as before, since moving the lock would hide a fixable setting. A service that
cannot run the request (no key, no model, no adapter) is refused before it may claim an empty or dead lock, so an
explicit pick of an unusable service never strands the episode on it.

## Amendment (2026-10-18)

**`replace` on describing an asset** (`adr-0024`). `DescribeAsset` joins the agent runs that need `replace: true`
before they write over saved text: without it the designer fills only the empty describable fields of the asset and is
refused with `CONFLICT` when none is empty, so a description typed by the creator is never rewritten by accident, in
either interface. The identity fields (a character's or a prop's name, a scene's location and time) are never written,
with or without `replace`. The MCP tool `describe_asset` carries the same flag (plan 07 phase E).

**The assets tools join iteration 1** (`adr-0024`, plan 07 phase E): `list_assets` (the project's library, or one
episode's assets with each character's outfit there), `create_asset`, `update_asset`, `delete_asset`, `design_assets`
and `extract_assets` (jobs, waited on with `wait_for_job`; a design has its own outcome), `describe_asset` and
`write_final_prompt`. `update_asset` is the one write without `ifRevision`: assets have no revision and the studio's
update is last-write-wins, so the instructions say to read before editing. `delete_asset` carries the
`requiresUserInteraction` meta and a `confirm` flag the server checks (`PRECONDITION_FAILED` without it, naming what
goes with the asset), the counterpart of the studio's confirmation dialog; the service's own refusal while an image
of the asset is being drawn is the same in both interfaces. `write_final_prompt` takes `replace` where the studio's
route takes `force`. Media paths (a character's views, an image, a voice sample), a voice and the sort order are not
fields of `update_asset`: media enter through the upload route and stay with the studio. The paid image requests
(`generate_asset_image`, an episode's outfit picture) and `set_episode_outfit` stay with iteration 2 and its
paid-generation opt-in; meanwhile the assistant sends the creator to the studio's asset library for the images.
