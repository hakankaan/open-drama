# ADR-0004 — SQLite through Drizzle ORM with migrations applied at startup

## Context

The app is self-hosted and single-user, so a single SQLite file gives zero-install deployment with no database server. The schema has to evolve across releases without losing user data, which rules out replaying `CREATE TABLE IF NOT EXISTS` DDL at boot: it has no history and cannot alter columns.

## Decision

**SQLite** (`better-sqlite3`, WAL, `busy_timeout`, `synchronous = NORMAL`) through **Drizzle ORM**, with **drizzle-kit generated SQL migrations committed under `apps/api/drizzle/`** and applied by the migrator at boot before anything else. Seeds (style presets) run after migrations and are idempotent and content-addressed (built-ins are upgraded only when unedited).

## Alternatives Considered

- **Postgres.** Better concurrency and multi-user story, but requires a server; wrong trade-off for a desktop-class tool. The Drizzle query layer keeps a later move possible.
- **DDL replay at boot.** Rejected: no reviewable history, no column changes.
- **Prisma.** Heavier runtime and engine binary; Drizzle maps more directly to SQL and to SQLite pragmas.

## Consequences

- Backups are file copies; the whole state is `data/`.
- Every schema change is a migration in a PR.
- Writes are serialised by SQLite; keep transactions short (batch shot upserts) and rely on WAL for readers during polling.
