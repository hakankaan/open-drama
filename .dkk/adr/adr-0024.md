# ADR-0024 — Assets designed from the story

## Context

A character, a scene or a prop is either typed into an empty dialog by hand or extracted from one episode's script by
the extractor. Nothing reads the story: the outline (adr-0015) names the recurring cast and the few places of the
world before any episode exists, but their reference images cannot be made until a script has been written and
extracted, because the prompt generator is an episode-scoped agent and an image request needs an episode whose image
lock it claims (adr-0016). The backlog item "seed the cast from the outline" and the request for AI help in creating
assets are the same need: a cast, places and props designed from the story, drawn before episode 1, and recognised by
the extractor when the scripts arrive. Plan 07 (`docs/plans/07-assets-from-story.md`) is the implementation plan; this
record holds its decisions, landed phase by phase.

## Decision

1. **A separate agent, not a mode of the extractor or the story writer.** The extractor catalogues what a script
   shows and links it to an episode; the story writer writes the outline the creator reviews first; the asset designer
   *invents a look* for what the story names, for the whole drama. The new agent `asset_designer` is drama-scoped
   (adr-0015), file-based (adr-0006), and shares the extractor's field rules through a shared skill so the two write
   the same kind of asset. (Plan 07 phase B.)
2. **A run offers a subset of its agent's tools.** `AGENT_TOOLS` stays the agent's full list (Settings shows it, the
   boot check reads it); every tool keeps its fixed scope (`defineTool` vs `defineDramaTool`), and a run without an
   episode is offered its agent's drama tools only. An agent may run in **both** scopes (today the prompt generator):
   it runs in the episode's context when the run has an episode and in the drama's otherwise, where its shot tools are
   withheld. The boot check keeps forbidding episode tools on a drama-scoped agent and requires an agent of both
   scopes to carry at least one drama tool. The tool ids a run offers are logged at trace level. A second use of the
   same rule, an allowlist the starting service names (so a describe run cannot call the bulk save), lands with its
   first caller in phase B. This amends adr-0015's rule that an agent's scope is fixed. (Phase A, landed.)
3. **Prompts and images without an episode.** `GenerateFinalPrompt.episodeId` and `RequestAssetImage.episodeId` are
   optional. With one, nothing changes: the episode's context and its locked image service, claimed at first use
   (adr-0016). Without one, the prompt generator runs in the drama's context and the image is submitted with no lock,
   in the explicit service, else the highest-priority active image service, as speech and lip sync already are
   (adr-0021); no episode lock is claimed. The project page's asset library generates prompts and images on its own and
   deletes an asset after confirmation. (Phase A, landed.)
4. **Drama-level assets, episode links by extraction.** The designer creates characters, scenes and props on the drama
   with no episode link; an episode's extraction links them (dedup by name) when the script uses them. The designer is
   refused without an outline (`412`) and while the outline is being written (`409`); it reads the outline once, through
   its read tool, and records the revision it saw in the job's progress. (Phase B, landed.)
5. **Three jobs, one per kind, like extraction; one save per run.** `design` is a drama-scoped job kind with a
   `target` of `characters`, `scenes` or `props`, one running job per target per drama (the existing partial unique
   index), the three in parallel, each judged by its one save tool having succeeded. The save tool takes the whole set
   in one call and caps it there (12 characters, 10 scenes, 5 props per run), naming the overflow in its reply so the
   agent does not retry. A designed character carries an appearance, a scene a prompt, a prop a description, and only
   the props may be an empty set; the extractor may still catalogue a name alone. (Phase B, landed.)
6. **The extractor's rules of merging apply.** Near-name dedup, fill-empty on existing rows, skip names that match
   only soft-deleted assets, skip an asset under claim, prompt staleness when a field the final prompt consumes
   changes; which fields those are becomes one per-kind list shared by the manual update, extraction, design and
   describe. (Phase B, landed.)
7. **The extractor may dress a designed character.** `save_dedup_characters` accepts an optional `outfit` per
   character, written through the outfit service's transaction (keyframes stale, adr-0023) only when the episode's
   outfit is empty; the character's own fields are not touched, a new character gets no outfit (its fields describe it
   as the script shows it), nor does a claimed one; the outfit image takes the character's claim. (Phase C, landed.)
8. **Describing one asset is synchronous, partial by default, and claimed.** `DescribeAsset` runs the designer for
   one existing asset in the request; each kind separates identity fields from describable ones; without `replace`
   the empty describable fields are filled and the call is refused only when none is empty; with `replace` (adr-0016)
   every describable field is rewritten and identity fields never are. One per-asset claim is shared by describe,
   final-prompt generation, the asset's image and its outfit image; a bulk save skips a claimed asset. The call is
   also refused while an image task of the asset is processing and while a design run of its kind runs, and it runs
   from the premise when there is no outline, since the request is explicit. Deleting an asset is refused the same
   way while its image task is processing, in both interfaces. The write goes through the manual update, so the
   prompt-staleness and keyframe-staleness rules of a hand edit apply to a description. (Phase D, landed.)
9. **Assistant parity without paid images.** MCP gets `list_assets`, `create_asset`, `update_asset` (last-write-wins,
   as the studio), `delete_asset` (`confirm`, the consent layer of adr-0016), `design_assets`, `extract_assets`,
   `describe_asset` and `write_final_prompt`. `generate_asset_image` and `set_episode_outfit` wait for the MCP
   catch-up and the paid-generation setting adr-0016 names as iteration 2. (Phase E.)

## Alternatives Considered

- **The story writer saves the assets with the outline.** Rejected: it doubles that agent's output budget, skips the
  creator's review of the outline, and leaves a pasted outline without assets.
- **The extractor runs on the outline.** Rejected: an episode-scoped agent whose tools link to an episode would need a
  drama scope and a second set of saves; the extractor catalogues what is shown, the designer invents what is told.
- **A second prompt agent for the drama scope** instead of one agent of both scopes. Rejected: it duplicates the
  prompt file and the four skills for one difference, the absence of shot tools.
- **A description revision carried on the image task and checked at completion**, so an image never attaches to an
  asset re-described while it was drawn. Left to the backlog: the same race exists for manual edits today, the stale
  flag on the prompt is the existing answer, and it is a change of the generation engine, not of this decision.
- **Asset revision tokens (`ifRevision`) on `update_asset`.** Rejected: assets have no revision column and the studio's
  update is last-write-wins; adding one for the assistant alone is a migration for no studio benefit.

## Consequences

- A cast can be drawn before episode 1: the library's prompts and images need no episode, and the first image made
  from the project page claims no episode's lock, so the episode's own first generation still picks and locks its
  service as before.
- The prompt generator is the one agent with tools of both scopes; the runtime, not the agent definition, decides
  which tools a run sees, and the trace log says which.
- Designed assets stay unlinked until an extraction links them; the episode's asset stage shows only linked assets,
  the project page's library shows all and deletes too.
- A renamed character in a later script is still a merge by hand (near-name dedup catches case and spacing, not
  renames); an image task still attaches its result whatever happened to the asset's fields while it ran (backlog).
- The status moves to accepted after the paid live run of plan 07 phase F.
