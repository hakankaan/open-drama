# ADR-0010 — Next.js serves the UI as its own process and proxies the API

## Context

Browser and API should share one origin. Serving a static SPA export from the API would give that, but Next.js App Router with dynamic routes (`/drama/[id]`) cannot be exported statically without known params, so the web app needs its own Node server.

## Decision

- The web app runs as its **own Next.js server** (`output: 'standalone'`) on `:3000`.
- A request-time proxy file (`proxy.ts`, the App Router's request hook) rewrites `/api/:path*` and `/static/:path*` to the API origin read from `API_ORIGIN` **at runtime** (default `http://localhost:4000`), so the browser sees a single origin, no CORS is needed, and the same build can point at any API host. `next.config` `rewrites()` are not used because they are frozen into the build.
- The Next.js proxy has a 30 s upstream idle timeout by default; it is raised (`experimental.proxyTimeout`, 15 minutes) because agent-backed endpoints (final prompt, single video prompt, agent chat) answer only when the agent run finishes and large media streams may stall.
- Development runs both processes with one root script; Docker runs both in one image behind one exposed port (`3000`), API bound to localhost.
- All pages are client-rendered against the API; there is no server-side data fetching.

## Alternatives Considered

- **Static export served by the API.** Rejected: dynamic routes; a catch-all client router would fight the framework.
- **Two exposed origins with CORS.** Kept as an escape hatch (`NEXT_PUBLIC_API_ORIGIN`) if proxying large media through Next proves slow; not the default.
- **Next.js route handlers as the API.** Rejected in `adr-0002`.

## Consequences

- Two processes to run and monitor instead of one; a healthcheck on the API and a start script that launches both.
- Media streams through the Next proxy; verify range requests and a paused-then-resumed `<video>` on a large file early (Plan 3 Phase 0, Plan 1 Phase 3).
- The API binds to `127.0.0.1` by default; only the web port is exposed. There is no authentication, so exposing that port exposes the whole tool (put a reverse proxy with authentication in front for anything beyond a private network).
- Long synchronous endpoints depend on the raised proxy timeout; anything that can take longer than a few minutes (extraction, breakdown, prompt batches, rewrite) is a job, not a request.

## Amendment (2026-10-09)

**Other sites cannot drive the tool.** With no accounts, a page on another site that reaches the port could spend the creator's keys, so both servers check requests.

- **The web proxy** refuses (403) `/api` and `/static` requests whose `Host` is not a name Open Drama answers to: localhost and `*.localhost`, IP literals, `PUBLIC_BASE_URL`'s name and the names in `OPEN_DRAMA_ALLOWED_HOSTS`. This stops DNS rebinding, and the proxy is the only place where the browser's Host is still visible.
- **The API** checks its own Host the same way, which covers rebinding straight to its port. It refuses unsafe methods the browser marks as not same-origin in `Sec-Fetch-Site`. From a browser too old to send that header, it refuses them when the `Origin` is neither the address the request went to (`X-Forwarded-Host` from the proxy, else `Host`) nor exactly the origin of `PUBLIC_BASE_URL` or `WEB_ORIGIN`. Another port or scheme on an allowed name is another site.
- **Requests without either header** do not come from a page, and pass.

A LAN name or a reverse proxy's domain must be listed in `OPEN_DRAMA_ALLOWED_HOSTS`.
