# ADR-0005 — One generation task lifecycle behind provider adapters

## Context

Images are generated for characters, scenes, props and shot frames; videos for shots. Providers differ in endpoint shape, sync/async behaviour, result encoding (URL vs base64), reference limits and error codes. One task table with per-provider adapters solves this, which is the right shape.

## Decision

One **generation task** aggregate and lifecycle for every image and video: `submit` (row created, service resolved explicit → episode lock → active) → `dispatch` (adapter builds the request, references normalised) → sync result or `poll` (profiles: images 5 s × 120 within 10 min; videos 10 s × 300) → `complete` (result persisted to local media, renditions derived, owner written back) or `fail` (classified error). Interrupted tasks are failed at boot.

Providers are **adapters** implementing `buildGenerateRequest / parseGenerateResponse / buildPollRequest / parsePollResponse / extractResult`, registered by provider name per service type, each carrying its reference limits and connectivity probe. The engine never contains provider-specific code.

## Alternatives Considered

- **Provider SDKs called directly from feature code.** Rejected: duplicates polling/persistence per feature and per provider.
- **An external job queue (BullMQ, Temporal).** Rejected for now: adds Redis/servers; in-process polling with DB-backed state is enough for one user. The lifecycle functions are queue-agnostic so a queue can be introduced later.

## Consequences

- Adding a provider is one file plus a probe.
- Every feature that needs media gets history, retry, status and write-back for free.
- The polling loop lives in the API process; restarts must be tolerated (they are: tasks fail and can be retried).

## Amendment (2026-10-09)

**An accepted task survives a restart** (`generation.ResumeInterruptedTasks`). Boot fails only the tasks no provider confirmed (no provider task id) and every stub task. A task that was already sent may still have run and been billed, and its error says so; telling the two apart would need a provider idempotency key, which is in the backlog. The others are polled again with their service row's address and key, provided the service still exists, has a key and names the same provider. A saved key never follows a service to another origin or provider without being entered again, and while a generation runs on a service, its provider, address and key cannot change and the service cannot be deleted (`configuration.UpdateModelService`, `configuration.DeleteModelService`), so a resumed task is polled where it was sent. The poll budget runs from the task's submission, so restarts never extend it. When the server stops, a task cut off mid-poll stays `processing` instead of being failed, so the next boot resumes it.

**Completion is guarded.**

- The provider's result URL is recorded before the download.
- The download is streamed to a temporary file. A timeout, a dropped connection or an HTTP 5xx, 429 or 408 is retried after 5 and 20 seconds.
- The task is written `completed` only while it is still `processing`. Its owner is updated only if the owner still exists, which for an asset means it has not been deleted.

Any failure after the provider finished leaves the URL on the task, so the media is not lost with the error.
