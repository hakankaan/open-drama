# Plan 7 — Assets from the story (designed cast, places and props)

Scope: AI help for creating assets. Today a character, a scene or a prop is either typed into an empty dialog by hand or extracted from one episode's script by the extractor. Nothing reads the story: the outline names the recurring cast and the few places of the world before any episode exists, but their reference images cannot be made until a script has been written and extracted. This plan adds an **asset designer**, a drama-scoped agent that turns the outline (and the premise, synopses and recaps around it) into a designed cast, the places of the world and the props the story turns on, with every field the image prompts need; makes final prompts and reference images possible **without an episode**, so the designed assets can be drawn before episode 1; lets the extractor dress a designed character for the episode instead of inventing them again; adds a one-asset **describe** action for assets made by hand; and gives the assistant the assets tools that need no paid image call. The script, storyboard and video pipeline are untouched.

Governing decisions: `adr-0006` (agents on the AI SDK tool loop, file-based prompts and skills), `adr-0008` (in-process, database-backed jobs), `adr-0015` (story development: the outline on the drama, drama-scoped jobs, the fixed scope of a tool), `adr-0016` (assistant access, replace and force, consent in the client, paid generation opt-in), `adr-0017` (prompt discipline), `adr-0018` (character views), `adr-0023` (per-episode outfits), `adr-0001` (every prompt and skill text is original). New: **`adr-0024` — Assets designed from the story** (this plan's §2 is its decision text). Domain: `.dkk/domain/contexts/{assets,agents,production}` plus a new flow `AssetDesign`; a step added to `AssetStage` and `AssistantStoryCreation`.

**Sequencing.** Builds on `e2d0f4d` (per-episode outfits, migration `0014`). No schema change and no migration: `agent_jobs.kind` is not constrained in the database, `target` already exists on every job, and the partial unique index `agent_jobs_running_drama_uq` on `(kind, drama_id, target)` already keeps one running drama-scoped job per target. `adr-0017` and `adr-0019` to `adr-0023` are still `proposed` pending their paid live run; this plan does not depend on any of them being accepted, and its own ADR follows the same rule (accepted after the live run in §5).

**Review.** Codex critiqued the first draft (2026-10-17), 14 findings. Accepted: a run offers a subset of its agent's tools (a describe run could otherwise call the bulk save; the prompt generator in a drama run must lose its shot tools), proven by the tool ids each mode offers; one save call per design run, since `runAgentUntilSaved` stops at the first successful save and per-call caps would not cap the job; `generate_asset_image` over MCP waits for the paid-generation opt-in `adr-0016` names as iteration 2 (no such setting exists yet); one per-asset claim shared by describe, prompt generation, the asset's image and its outfit image, with the bulk saves skipping a claimed asset; `ifRevision` dropped from `update_asset` (assets have no revision column, the studio's update is last-write-wins); the outline revision recorded by the read tool that saw it, and a `design` variant of `JobOutcome`; one delete contract for both transports (`confirm` is the consent layer, no `force`), plus a refusal while the asset's image task runs; the per-kind list of fields the final prompts consume, shared by the manual update, extraction, design and describe (today extraction and the update stale a character's prompt on `appearance`/`styling` only, while the prompt reads `role` and `description` too); describable fields separated from identity fields for the describe rule; extraction's outfit written through the outfit service's transaction so keyframes go stale (`adr-0023`); delete in the project's asset library and a retry-safe create-then-describe; phase A's service-resolution proof with stubs off (the stub adapter answers before any service is looked at); the web `PREFIX` record; `200` not `202`. Rejected: a description revision carried on the image task and checked at completion (an image requested from an asset that is edited while the task runs attaches today too, for manual edits; the stale flag is the existing answer, and the hole is recorded in `docs/BACKLOG.md` as pre-existing, not widened by this plan).

## 1. Goals

1. **Cast, places and props from the story.** With an outline on the drama, one click (or one MCP call) designs the characters the outline names, the places of its world and the props its threads turn on, at drama level, with every descriptive field filled in the way the image prompts need. Existing assets are read first and never duplicated; a hand-made asset with empty fields is completed, one with filled fields is left alone.
2. **Images before episode 1.** A designed asset gets its final prompt and its reference images (a character's views, `adr-0018`) without any episode: the project page's asset library generates them on its own, using the project's image service instead of an episode's lock.
3. **One story, one cast.** When a script is later extracted, the extractor recognises the designed cast by name and links them instead of inventing a second version; where the episode dresses a character differently from their designed look, the extractor records that as the episode's outfit (`adr-0023`) rather than overwriting the character.
4. **Help for one asset.** A character, scene or prop created by hand with only a name can be described by the designer in the same style, from the story; the creator keeps the fields they filled.
5. **The assistant can design, describe and manage.** The MCP server gets `list_assets`, `create_asset`, `update_asset`, `delete_asset`, `design_assets`, `describe_asset`, `extract_assets` and `write_final_prompt`; the assistant's story-creation skill continues from the outline to a designed cast and sends the creator to the studio to draw it. Drawing images from the assistant (`generate_asset_image`, and the rest of the production floor) stays with the MCP catch-up, behind the paid-generation setting and per-call caps `adr-0016` calls iteration 2.
6. **Offline proof.** Every agent path runs on the stub stack (`OPEN_DRAMA_STUB_PROVIDERS=1`) with deterministic output; service resolution without an episode is proven with stubs off and no paid call; one paid live run on a real text and image provider, with consent, before `adr-0024` is accepted.

Non-goals: a wardrobe library (`docs/BACKLOG.md`), designing assets from a pasted script rather than the outline (the extractor does that per episode), voices (`adr-0021` pins a voice when lines are first spoken), keyframes or anything below the asset stage, automatic image generation after a design run (images cost money and are requested explicitly, as today), paid generation over MCP, asset revision tokens.

## 2. Decisions (ADR-0024)

1. **A separate agent, not a mode of the extractor or the story writer.** The extractor catalogues what a script shows and links it to an episode; the story writer writes the outline the creator reviews first; the asset designer *invents a look* for what the story names, and does it for the whole drama. Folding it into the story writer would double that agent's output budget and skip the creator's review of the outline; folding it into the extractor would give an episode tool a drama scope. The new agent `asset_designer` is drama-scoped (`adr-0015`), file-based (`workspace/prompts/asset_designer.md`, skills under `asset-designer/`), and shares the extractor's field rules through a shared skill so the two write the same kind of asset.
2. **A run offers a subset of its agent's tools.** `AGENT_TOOLS` stays the agent's full list (Settings shows it, the boot check reads it); the service that starts a run names the tools this run may call, and the runtime hands the tool loop only those, minus every episode tool when the run has no episode. So a design run offers the story read, the existing-asset reads and one bulk save; a describe run offers the story read, one existing-asset read and one single-asset describe tool, and cannot create assets; the prompt generator in a drama run offers its asset tools and not its shot tools. This amends `adr-0015`'s rule that a tool's scope is fixed by its agent: the scope is still fixed per tool (`defineTool` vs `defineDramaTool`), and an agent may now have both kinds, with the boot check requiring that every episode tool of such an agent is one a drama run can do without. The tool ids a run offers are logged at trace level, which is how the proofs read them.
3. **Drama-level assets, episode links by extraction.** The designer creates characters, scenes and props on the drama with no `episode_*` link; an episode's extraction links them (dedup by name) when the script uses them. The designer runs after the outline exists and is refused without one (`412`), and refused while the outline is being written (`409`), as the planner is; the outline may be edited while the designer runs (the run reads it once, through its read tool, and records the revision it saw).
4. **Three jobs, one per kind, like extraction; one save per run.** `design` is a new drama-scoped job kind with a `target` of `characters`, `scenes` or `props`; one job per target at a time per drama, the three in parallel, each judged by its one save tool having succeeded (`runAgentUntilSaved`, one retry). The save tool accepts the whole set in one call and caps it there: at most 12 characters, 10 scenes or 5 props per run (an outline's cast is "4–6, named as in scripts"; the world has "a few places"), the overflow named in the tool's reply so the agent does not retry. The extractor's per-episode cap of 3 props is unchanged.
5. **The extractor's rules of merging apply.** Saving designed assets uses the extraction merge: near-name dedup, fill-empty on existing rows, skip names that match only soft-deleted assets, skip an asset under claim (§2.8), prompt staleness when a field the final prompt consumes changes. Which fields those are becomes one per-kind list in the assets module, used by the manual update, extraction, design and describe alike.
6. **Prompts and images without an episode.** `GenerateFinalPrompt.episodeId` and `RequestAssetImage.episodeId` become optional. With one, nothing changes (the episode's lock and its context). Without one, the prompt generator runs in the drama's context (§2.2) and the image is submitted with no lock (`lockedServiceId: null`, no `lockFor`): the explicit service, else the highest-priority active image service, as speech and lip sync already do; no episode lock is claimed.
7. **The extractor may dress a designed character.** `save_dedup_characters` accepts an optional `outfit` per character: for an existing character whose look differs in the episode, the outfit text is written through the outfit service's transaction, which stales the episode's keyframes bound to that character (`adr-0023`), and only when the episode's outfit is empty; the character's own fields are not touched. A new character gets no outfit from extraction (their fields describe them as the script shows them).
8. **Describing one asset is synchronous, partial by default, and claimed.** `DescribeAsset` runs the designer for one existing asset in the request, like `Generate*FinalPrompt`. Each kind separates its *identity* fields (a character's `name`; a scene's `location` and `time`; a prop's `name`) from its *describable* fields (`role`, `description`, `appearance`, `styling`; `prompt`, `lighting`; `type`, `description`). Without `replace`, the designer fills the empty describable fields and the call is refused `409 CONFLICT` only when none is empty; with `replace` (`adr-0016`) every describable field is rewritten and identity fields never are. The asset's claim, today taken for the prompt agent and the image submission, is shared by describe, final-prompt generation, the asset's image request and its outfit image request, so none of them runs over another; a bulk save skips a claimed asset. The create dialog's "Describe with AI" creates the asset from what was typed, then describes it; if the agent fails, the created asset stays and the dialog opens it, so a retry describes rather than creates again.
9. **Assistant parity without paid images.** MCP gets `list_assets`, `create_asset`, `update_asset` (last-write-wins, as the studio), `delete_asset` (`confirm`, the consent layer of `adr-0016`; refused `409` while an image task of the asset runs, in both transports), `design_assets` and `extract_assets` (returning `JobStarted`, waited on with `wait_for_job`, with a `design` outcome), `describe_asset` (`replace`) and `write_final_prompt` (`episodeId` optional), each a thin mapping of the service call. `generate_asset_image` and `set_episode_outfit` wait for the MCP catch-up and the paid-generation setting.

## 3. Behaviour to guarantee

1. `POST /api/v1/dramas/:id/design {target}` with an outline returns `200 {jobId, alreadyRunning}` like the outline and plan starts; the job reads the premise, the outline, the episodes' synopses and recaps, and the existing assets of the kind, and saves the designed ones in one call. Without an outline: `412 PRECONDITION_FAILED "Write the outline first"`. While an outline job runs: `409`. While the same target's design runs: the running job with `alreadyRunning: true` (the `runJob` rule). The three targets run in parallel.
2. The save is one transaction per run: a name matching an existing active asset (near-name rule) fills that asset's empty fields and never overwrites a filled one; a name matching only a soft-deleted asset is skipped; an asset under claim is skipped; new names are inserted on the drama with no episode link; the caps of §2.4 are enforced in the tool with the overflow named in the reply. Two parallel runs (design and an episode extraction) cannot insert the same name twice: better-sqlite3 transactions are synchronous, and the dedup read is inside the transaction. The tool's reply and the job's `progress` carry `{saved, filled, skipped, overflow}`.
3. Filled fields read like the extractor's: a character has `role`, `description`, `appearance` (age, build, face, hair, skin, distinguishing marks; no outfit, which belongs to `styling`), `styling` (the default look they are usually drawn in); a scene has `location`, `time`, `prompt` (set dressing), `lighting`; a prop has `type`, `description`. Narrators and voices without a body are not characters. The designer names characters exactly as the outline's Cast lines do, so a later script and its extraction match.
4. `DramaJobs` gains `design: {characters, scenes, props}` (each `AgentJob | null`); the job's `progress` carries the `outlineRevision` the read tool saw and the save counts; `wait_for_job` returns a `design` outcome `{kind, target, saved, filled, skipped, outlineRevision}`. The studio shows the three runs on the project page with cancel, and a note when the outline's revision moved past the last design's.
5. A run offers only its allowed tools: a design run `read_story_for_design`, `read_existing_<kind>`, `save_designed_<kind>`; a describe run `read_story_for_design`, `read_existing_<kind>`, `describe_<kind>`; a prompt-generator run without an episode `read_<kind>s` and `save_<kind>_final_prompt` only, with an episode the full list as today. The boot check accepts the prompt generator's mixed list and rejects an episode tool on a drama-scoped agent as before.
6. `POST /characters/:id/final-prompt {}` (no `episodeId`) runs the prompt generator in the drama's context and saves the prompt with the style prefix; `POST /characters/:id/image {views}` without an `episodeId` submits the views chain with no lock, on the explicit service or the highest-priority active image service, and refuses with the `412` `resolveGeneration` already raises ("Add an active image service with an API key in Settings …") when there is none. With an `episodeId`, both behave exactly as today (the episode's lock, `lockFor` at first use). `videoPromptBatch` (the prompt generator per shot) is unchanged.
7. The asset library on the project page generates final prompts and images without an episode, and deletes an asset after confirmation; its "needs an episode" copy goes. The episode's asset stage still generates under the episode's lock.
8. Extraction over a designed cast: a character named in the script and already on the drama is linked to the episode and not re-described; when the extractor sends an `outfit` for them and the episode's outfit is empty, it is saved through the outfit service (keyframes bound to the character in that episode go stale, `outfitPath` stays null, the outfit picture is requested as today). A filled episode outfit is kept.
9. `POST /characters/:id/describe {replace?, model?, textServiceId?}` fills the empty describable fields from the story (`200` with the asset); with none empty and no `replace`: `409 CONFLICT "The character is already described; pass replace to write over it"`; with `replace`, every describable field is rewritten, identity fields untouched, the final prompt marked stale. Refused `409` while the asset is claimed (its image, outfit image or another describe or prompt generation in flight) or while an image task of the asset is processing, and while a design run of its kind runs. Without an outline the designer still runs, from the premise and the asset's fields (the request is explicit, unlike a design run).
10. The create dialog has "Describe with AI" beside "Create": it creates the asset with the name and whatever fields were typed, then describes it; on failure the asset exists and the detail dialog opens on it with the error. The detail dialog has "Describe" (some describable field empty) and "Describe again" (asks to confirm, sends `replace`).
11. MCP: every tool of §2.9 is registered through `tool()` with contract input and output and the right annotations (`list_assets` read-only, `delete_asset` confirm, `update_asset` idempotent); `design_assets` without an outline returns the `412` text; `describe_asset` on a fully described asset returns the `409 CONFLICT` text unless `replace`; `delete_asset` while the asset's image task runs returns `409`; `write_final_prompt` without an episode writes the prompt. `get_status` is unchanged.
12. Stub stack: the stub model designs from the outline deterministically (names from Cast lines, places from the World section, props from the Threads section), fills fields with marked text, describes one asset the same way, and the whole flow (design → prompts → images → episode extraction linking the designed cast with an outfit) runs offline end to end.
13. The workspace template goes to version 12: new prompt and skills, the shared field rules, the prompt generator's and the extractor's amended texts, the new assistant skill, and the upgrade merges them under the hash rule (unedited files replaced, edited ones kept and reported).

## 6. Risks and open points

- **Names that drift.** The designer names characters as the outline's Cast lines do, and the episode writer is told (through the outline) to use those names; a script that renames one ("Mei" to "Mei Lin") makes the extractor insert a second character. The near-name rule catches case and spacing, not renames. Mitigation: `read_existing_characters` lists the designed cast to the extractor with the instruction to prefer an existing name; a rename stays a creator's merge by hand (backlog).
- **Scenes need a time of day.** The outline describes places, not moments; the designer picks the time the Story section implies most, and the extractor's near-name rule treats `location + time` as the scene key, so an episode at night in a designed daytime place inserts a second scene. That is correct (a different picture), and the designer's skill says to prefer the place's most common time and to leave the exotic ones to extraction.
- **A design run reads the whole story.** Premise, outline (≤20k), synopses and recaps: within the budget `adr-0014` sets for the series block, one call per run, three runs in parallel; the cost per run is that of an outline write, three times. The Story tab says so beside the button (the assistant skill too).
- **One save call per run.** Twelve characters with four fields each is one tool call of a few thousand tokens, within every configured model's output limit; a provider that cuts the call fails the run (one retry, then the job fails with what the tool reported), and the creator can lower the ask by trimming the outline's cast. Saving in batches was rejected: `runAgentUntilSaved` judges the run by its first successful save, and per-call caps would not cap the job.
- **A run's tool subset.** The allowlist is the one new runtime rule; a service that names a tool the agent does not have is a boot-time mistake, so `checkAgentToolScopes` also checks every allowlist the services declare (they are constants beside `AGENT_TOOLS`).
- **Images and edits still race at completion.** An image task attaches its result whatever happened to the asset's fields while it ran (a manual edit today, a bulk fill tomorrow); the stale flag on the prompt is what tells the creator. A description revision on the task, checked at completion, was considered and left to the backlog: it is a change of the generation engine, not of this plan.
- **Designed assets are unlinked.** Until a script is extracted, a designed character is on the drama but in no episode; the episode's asset stage shows only linked assets, the project page's library shows all and now deletes too.
- **Describe from a bare premise.** Without an outline the designer has little to go on and invents more; the request is explicit, so it is allowed, and the dialog says the outline makes it better.
- **No images from the assistant yet.** The assistant designs and describes, then points to the studio's library; `generate_asset_image` arrives with the paid-generation setting and per-call caps of the MCP catch-up, together with the other production-floor tools.
- **Open:** whether `ExtractionJob` is extended or `DesignJob` added in the domain model (decide in phase B with the aggregate in front).
